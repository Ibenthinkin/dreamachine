**URL rotation: the old project gets parked, not deleted.** Working out how to change the live URL surfaced the constraint that decides the whole approach — Cloudflare has **no rename for a Pages project**. The hostname is literally `<project-name>.pages.dev`, fixed at creation, so "change the URL" can only mean a new project under a new name. Adding a custom domain doesn't substitute: it leaves the old `pages.dev` serving alongside it.

The non-obvious part is what happens to `dreamachine-s5k` afterwards. Deleting it **releases the name back to Cloudflare's pool**, so anyone could then create a project called `dreamachine-s5k` and serve whatever they like at the exact URL sitting in commit `cd21b52` — which a reader of this repo's history would reasonably trust. That's the inverse of what pulling the demo link was for: a stranger lands on someone else's page rather than a dead one. So the old project stays alive and inert instead: it keeps the name permanently and guarantees the historical link resolves to nothing.

**Built the `parked` branch** (`0ce6293`) — an orphan branch, no shared history with `main`, no application code: `index.html` (static notice, no JS), a byte-identical `404.html` so deep links land on it too, `robots.txt` disallowing all plus a `noindex` meta tag, and a README explaining why the branch exists so a future session doesn't "fix" it. **Four dashboard traps, recorded because each one cost a round trip:**

- **The dashboard funnels repository imports into Workers, not Pages.** "Create application → Import a repository" builds a *Worker*; the Pages path is a small line of text at the bottom of the create dialog. Got a Hello World Worker twice before spotting it. **The tell is the settings page:** Workers has a *deploy command* and no *build output directory* (it reads the output location from `wrangler.jsonc`'s `assets.directory`); Pages has a build output directory and no deploy command. Check which fields exist before debugging anything else.
- **Workers is the wrong platform here for a privacy reason, not a technical one.** Workers Builds requires the worker name in a committed `wrangler.jsonc`, and the account subdomain is a `<name>-<3 digits>` shape — trivially enumerable. Publishing the worker name in a public repo would effectively publish the URL and defeat the entire rotation. Pages keeps the project name dashboard-side. Same argument rules out a custom domain, which would put the hostname in public Certificate Transparency logs within minutes; `pages.dev` sits behind a Cloudflare wildcard cert and never appears in CT. **The platform subdomain is the more private option, not the lazier one.**
- **The Next.js framework preset applies `@opennextjs/cloudflare`, which cannot build a static export.** It expects `.next/standalone/` and dies on `ENOENT … pages-manifest.json`. This repo is `output: "export"` — there is no server. Build command must be plain `bun run build` with output `out`. (The `worker_threads` NotImplementedError noise Bun emits above that failure is a red herring.)
- **Production branch and build configuration live in different settings sections, and the production-branch change silently failed to persist twice.** Symptom: builds land as *Preview*, and the bare host keeps serving the last successful production deployment. Retrying a preview only ever produces another preview — promotion needs a fresh push once the production branch is actually set. **The diagnostic that isolates this in one shot is the branch alias:** `<branch>.<project>.pages.dev`. `parked.…` serving the notice while the bare host served the app proved the build was fine and the fault was the production-branch setting alone. Reach for it before touching build config.
